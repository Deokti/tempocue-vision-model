# Правила оформления коммитов

Перенесены из основного репозитория TempoCue (`docs/commits.md`) и адаптированы:
формат и требования те же, таблица scope — своя. Репозитории разные, история —
общая по духу: понятная человеку и объясняющая причины решений.

Используется [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/).

## Формат

```text
<type>(<scope>)!: <description>

[необязательное тело]

[необязательные сноски]
```

Обязательны `type`, `scope` и `description`. Знак `!`, тело и сноски — при
необходимости.

## Язык и написание

- `type` и `scope` — на английском строчными буквами; составной scope в
  `kebab-case`.
- Описание и тело — на русском. Описание начинается со строчной буквы,
  формулируется как действие в неопределённой форме: `добавить`, `исправить`,
  `измерить`, `перенести`. Точка в конце заголовка не ставится.
- Заголовок описывает результат, а не процесс. Без `правки`, `update`, `WIP`.

## Типы

Как в основном репозитории: `feat`, `fix`, `docs`, `refactor`, `test`, `perf`,
`build`, `ci`, `chore`, `style`, `revert`. `feat` — только новая
функциональность, `fix` — только исправление дефекта, `refactor` не скрывает
изменение поведения, `chore` не заменяет более точный тип.

## Scope

Scope называет одну область ответственности этого репозитория:

| Scope | Область |
| --- | --- |
| `repo` | каркас, окружение, структура, правила репозитория |
| `formats` | чтение `.tempocue-vision` / `.tempocue-sequence` и разметки |
| `render-check` | сверка отрисовки: шумовой пол, отрисовщик, перебор, отчёт |
| `ddragon` | загрузка и кэш ресурсов Data Dragon |
| `generator` | генератор синтетических кадров и разметки |
| `detector` | детектор центров «где» |
| `embedding` | вложение «кто» и прототипы |
| `training` | общая обучающая обвязка: циклы, метрики, чекпоинты |
| `export` | экспорт в ONNX и файлы соответствия |
| `docs` | документация, не относящаяся к более точной области |
| `deps` | зависимости |

Список не закрытый: новый scope разрешён, когда существующие не выражают
владельца изменения, и не должен быть синонимом существующего.

## Тело коммита

Тело обязательно для нетривиального изменения и отвечает на «зачем?» и «какие
ограничения учтены?», не пересказывая diff. Структура:

1. какая проблема или ограничение существовали;
2. почему прежний подход был недостаточен;
3. что изменено на уровне поведения или решения;
4. чем подтверждён результат: замером, картинкой, прогоном инструмента;
5. какие ограничения или следующие шаги остались.

Конкретные факты — имя кадра, число чемпионов, измеренный остаток —
предпочтительнее общих фраз. Не заявлять, что задача решена полностью, если
проверен один пример.

## Сноски

Формат Git trailer, отделяются пустой строкой. Вымышленные номера задач не
добавляются. **`Co-Authored-By` для ИИ-ассистентов не добавляется**: автором
коммита остаётся разработчик, который проверил и принял изменение.

## Критические изменения

`!` перед двоеточием и сноска `BREAKING CHANGE:` — если ломается формат,
который читает кто-то ещё: схема датасета, контракт ONNX-артефакта, формат
файла соответствия.

## Атомарность

- Один коммит — одно законченное намерение.
- Случайное форматирование, временные файлы и несвязанные исправления в коммит
  не входят; `out/`, `data/`, датасеты и веса не коммитятся вовсе.
- Код и относящиеся к нему документы/результаты ступени могут идти одним
  коммитом: тип выбирается по основному намерению.
- Неопубликованную историю можно править (`--amend`); опубликованную — нет.

## Проверка перед коммитом

1. `git status --short` содержит только ожидаемые файлы.
2. Staged diff выражает одно намерение; без секретов, Riot ID, крупных
   артефактов.
3. Тип точный, scope один и из таблицы (или осознанно новый).
4. Заголовок читается без просмотра diff.
5. Затронутые инструменты прогнаны, картинки проверены глазами — либо в теле
   явно сказано, что не проверялось и почему.
